CRITICAL Mid-stream API failure replays the turn — JARVIS double-speaks — claude_brain.py:553 (brain+speech)
In respond_stream, if the Anthropic API stream (_api_stream_chat) yields one or more sentence chunks and THEN raises (network blip, mid-stream refusal, connection reset), those chunks have already been yielded and spoken (produced=True). The exception jumps over the `if produced: return` (lines 559-560), is swallowed by `except: pass` (561-562), and execution falls through to the subprocess block (563) which re-runs the ENTIRE turn via _stream_once/_run_once. The user hears the first sentence(s) twice, then a second full reply. The identical bug exists in the subprocess branch at 563-572: a mid-stream error after producing chunks falls through to the one-shot fallback (574) which speaks the whole reply again. The `if produced: return` only protects against errors that occur BEFORE the first chunk; any error after the first chunk causes a replay.
Fix: Track `produced` across the whole function and gate the fallbacks on it: once any chunk has been yielded, do NOT fall through to a lower tier — either `return` from the except block, or wrap each tier so a post-first-chunk error ends the generator. e.g. `except Exception: \n if produced: return \n pass` in both the API block (561) and the subprocess block (571), and guard the one-shot fallback (573-585) with `if not produced:`.
CRITICAL No busy_timeout set — concurrent writers raise 'database is locked' and crash the turn — memory.py:27 (memory+db)
_get_db() opens a fresh connection and enables WAL but never sets PRAGMA busy_timeout (default 0). The same data/jarvis.db is written concurrently from multiple contexts every turn: log_turn runs via asyncio.to_thread (server.py:2628-2629), extract_memories calls remember() as a background task (server.py:2657), record_action runs from dispatch tasks, and recall() issues an UPDATE on the event loop. With WAL, readers don't block writers but two writers still serialize, and with busy_timeout=0 the loser immediately raises sqlite3.OperationalError: 'database is locked'. Fix: In _get_db() add conn.execute('PRAGMA busy_timeout=5000') (and ideally synchronous=NORMAL). Wrap the write helpers in try/except that logs and degrades gracefully. Consider a single serialized writer or a module-level lock for the writer path.
